# Data Center Monitoring Backend — Group 3

Backend, API, and database implementation for **Group 3** of the Data Center Monitoring project from Anhanguera Osasco.

The application was developed with **Python, Flask, SQLAlchemy, and MySQL/SQLite**. Its role is to receive monitoring data sent by server agents, validate and store this information, maintain the history of metrics, manage monitored servers, and create or resolve resource-usage alerts.

The source code is standardized in **English**, while the API also provides **Portuguese aliases** for compatibility with the project guide and with other groups.

---

## 1. Project objective

This backend acts as the central processing layer of the monitoring system.

The expected flow is:

```text
Monitored server
      ↓
Monitoring agent
      ↓
POST /monitoring
      ↓
Flask API
      ↓
Validation and processing
      ↓
Database persistence
      ↓
Alert verification
      ↓
Data available to the dashboard
```

When a monitoring agent sends CPU, memory, disk, and other server information, the API:

1. validates the received JSON;
2. checks whether the monitored server already exists;
3. creates the server automatically if necessary;
4. updates the server information if it already exists;
5. stores a new metric record;
6. checks CPU, memory, and disk usage;
7. creates alerts when the configured limit is reached;
8. resolves active alerts when the metric returns to normal;
9. makes the stored data available through GET endpoints.

## 4. Main files and responsibilities

### `app.py`

Main application file.

It is responsible for:

- creating the Flask application;
- loading the project configuration;
- initializing SQLAlchemy;
- enabling CORS;
- registering the API blueprints;
- importing the models;
- creating database tables with `db.create_all()`;
- exposing the root `/` endpoint;
- starting the application on port `5000`.

The application uses an application factory:

```python
app = create_app()
```

This keeps initialization centralized and makes the project easier to maintain and test.

### `config.py`

Centralizes the application configuration.

The database connection follows this priority:

1. use `DATABASE_URL` if it exists;
2. otherwise build a MySQL URL using the `DB_*` variables;
3. if MySQL is not configured, use local SQLite automatically.

Default local database:

```text
sqlite:///monitoring.db
```

CORS can also be configured through:

```text
CORS_ORIGINS
```

If it is not defined, the default value is `*`.

### `database/db.py`

Creates the shared SQLAlchemy instance:

```python
db = SQLAlchemy()
```

The same object is imported by the models, routes, and services so the entire application uses the same database session.

## 5. Database models

### `Server`

Represents each monitored server.

Main fields:

- `id`
- `name`
- `ip`
- `operating_system`
- `status`
- `last_check`

The IP is unique and is used by the monitoring route to identify whether a server already exists.

### `Metric`

Stores the monitoring history received from each server.

Main fields:

- `id`
- `server_id`
- `cpu_percent`
- `memory_percent`
- `disk_percent`
- `network_percent`
- `timestamp`

Every valid monitoring request creates a new metric record.

### `Alert`

Stores resource alerts generated by the backend.

Main fields:

- `id`
- `server_id`
- `alert_type`
- `level`
- `message`
- `status`
- `created_at`

Current alert types generated automatically by the backend:

```text
CPU
MEMORY
DISK
```

Current statuses:

```text
ACTIVE
RESOLVED
```

### `Service`

Provides the database structure for monitored services such as HTTP, SSH, API, database services, or other endpoints.

Main fields include service name, type, port, status, response time, and last check.

The model and SQL table are prepared, but the current API does **not** expose service endpoints yet.

### `Event`

Provides the structure for storing events and availability history.

The model contains information such as server, history message, unavailability status, and timestamp.

The model and SQL table are prepared, but automatic offline detection is **not** implemented in this backend. The current backend only stores the `ONLINE` or `OFFLINE` status when that status is provided by another component.

## 6. Routes and API endpoints

The English endpoints are the canonical routes. Portuguese aliases are available for compatibility.

| Method | English route | Portuguese alias | Purpose |
|---|---|---|---|
| GET | `/` | — | Check whether the backend is online |
| POST | `/monitoring` | `/monitoramento` | Receive monitoring data |
| GET | `/servers` | `/servidores` | List monitored servers |
| GET | `/servers/<id>` | `/servidores/<id>` | Get one server |
| GET | `/metrics` | `/metricas` | List metric history |
| GET | `/alerts` | `/alertas` | List alerts |
| PUT | `/alerts/<id>/resolve` | `/alertas/<id>/resolver` | Resolve an alert manually |

Metrics can be filtered by server using either parameter:

```text
/metrics?server_id=1
/metricas?servidor_id=1
```

Alerts return only active alerts by default:

```text
GET /alerts
```

To retrieve all alerts, including resolved ones:

```text
GET /alerts?status=ALL
```

## 7. Monitoring payload

### English format

```json
{
  "server": "SRV-01",
  "ip": "192.168.56.11",
  "cpu": 42,
  "memory": 58,
  "disk": 65,
  "network": 10,
  "operating_system": "Ubuntu Server 22.04",
  "status": "ONLINE",
  "timestamp": "2026-10-05T12:00:00"
}
```

### Portuguese-compatible format

```json
{
  "servidor": "SRV-01",
  "ip": "192.168.56.11",
  "cpu": 42,
  "memoria": 58,
  "disco": 65,
  "rede": 10,
  "sistema_operacional": "Ubuntu Server 22.04",
  "status": "ONLINE",
  "data_hora": "2026-10-05T12:00:00"
}
```

Accepted aliases:

| Canonical field | Portuguese alias |
|---|---|
| `server` | `servidor` |
| `memory` | `memoria` |
| `disk` | `disco` |
| `network` | `rede` |
| `operating_system` | `sistema_operacional` |
| `timestamp` | `data_hora` |

`cpu`, `ip`, and `status` use the same name in both formats.

### Required fields

The API requires:

```text
server/servidor
ip
cpu
memory/memoria
disk/disco
```

`network/rede` is optional and defaults to `0`.

`operating_system/sistema_operacional`, `status`, and `timestamp/data_hora` are also optional.

When no timestamp is sent, the backend uses the current server time.

## 8. Validation rules

The monitoring endpoint validates incoming data before storing it.

CPU, memory, disk, and network values must be numeric and must remain between:

```text
0 and 100
```

Accepted status values:

```text
ONLINE
OFFLINE
```

The timestamp must use ISO 8601 format, for example:

```text
2026-10-05T12:00:00
```

or:

```text
2026-10-05T12:00:00Z
```

Invalid requests return HTTP `400` with an error message.

## 9. Alert system

Alert logic is implemented in:

```text
services/alert_service.py
```

The current threshold is:

```python
ALERT_THRESHOLD = 85
```

The backend monitors:

```text
CPU
Memory
Disk
```

### Alert creation

If a monitored value is equal to or greater than `85%`, an active alert is created.

Example:

```text
CPU = 90%
```

Result:

```text
CPU alert → ACTIVE
```

### Duplicate prevention

If CPU remains above the threshold in later monitoring requests, the backend checks whether an active CPU alert already exists for that server.

If an active alert already exists, another one is **not** created.

This prevents the database from creating a new alert every time the agent sends the same high metric.

### Automatic resolution

When the metric returns below `85%`, active alerts for that metric are changed to:

```text
RESOLVED
```

Example:

```text
First request: CPU = 92% → creates CPU alert
Second request: CPU = 91% → keeps the same active alert
Third request: CPU = 40% → resolves the active CPU alert
```

Alerts can also be resolved manually using the API.

## 10. Database configuration

### Option A — Local test with SQLite

No database environment variables are required.

If MySQL variables are not configured, the application automatically uses:

```text
sqlite:///monitoring.db
```

This is the simplest option for testing the backend locally.

### Option B — MySQL

Create a `.env` file in the project root:

```env
DB_USER=root
DB_PASSWORD=your_password
DB_HOST=localhost
DB_PORT=3306
DB_NAME=monitoring
CORS_ORIGINS=*
```

The MySQL database itself must exist before SQLAlchemy can connect to it.

A database creation script is available at:

```text
sql/database.sql
```

It creates:

```sql
CREATE DATABASE IF NOT EXISTS monitoring;
```

The project also contains individual SQL scripts for all tables and indexes. They can be used for manual database creation or as a reference for the schema.

Because `app.py` executes `db.create_all()`, SQLAlchemy can automatically create the tables in an existing configured database.

```text

3. Send metrics to POST /monitoring.
4. Confirm that the server appears in GET /servers.
```
